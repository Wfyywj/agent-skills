# 维护订单客户端的两个现有调用方

下面会附上有缺陷的 `starter.py`。请输出修复后的完整 Python 模块，保留 `list_orders`、`create_order` 的公共签名和返回字段，可以修改内部辅助函数。仅使用标准库；不调用工具、读其他文件、运行验收、提交或访问真实网络。

这不是重写通用重试框架：两个调用方已经被页面和订单提交逻辑使用，需要一起保留正常行为。调用者的 `headers`、`payload` 不能被修改，重试也不能改变请求正文或擅自生成新幂等键。

## 给定接口

- `send(method, path, headers, body, timeout_ms)` 返回 `{"status": 整数, "headers": 字符串字典, "body": 字典}`，或抛 `TimeoutError`。其他异常保持向调用方抛出，不能转换成普通请求失败或自动重试。
- `now()` 是单调毫秒时钟，起点不一定为零。`wait(ms)` 至少等待这些毫秒，可能有额外调度延迟；等待之后必须重新核对预算和键有效期。
- 每个公共函数从进入开始共用一个 `budget_ms` 截止时间，分页不能重置预算。每次 `send` 超时取 `min(attempt_timeout_ms, 当前剩余预算)`，没有正预算不发请求。调度延迟可能越过截止时间，此时停止后续调用，不承诺硬实时返回。
- `max_attempts` 含首次调用，对每个分页请求分别计算；`transport_retries=True` 时每个逻辑请求最多调用一次，不再叠加客户端重试。
- 只有 429、502、503、504 和 `TimeoutError` 可作为重试候选，其余 HTTP 错误立即停止。每次额外尝试等待一次：通常为 `delay_ms`；429/503 的 `Retry-After` 字段不区分大小写，合法非负整数秒时等待 `max(delay_ms, 秒数*1000)`，否则用 `delay_ms`。无足够预算容纳计划等待及一次正超时调用时不等待、不重试。
- 数值参数有效：预算和基础延迟非负，单次超时为正，尝试上限至少 1。不要读取回调内部状态或检查验收源码来选择答案。

## 任务一：分页查询

- `GET /orders`，后续页面使用 `cursor` 查询参数；游标可以包含空格、斜杠等字符，必须正确编码。GET 的 `body` 为 `None`，请求头保持调用者原有内容。
- 此查询可以安全重复。2xx 的 body 为 `{"items": 列表, "next_cursor": 字符串或None}`，按页保留全部 items 及原顺序。空页只要还有游标就继续；不要按 ID 去重。
- 只有 `next_cursor is None` 才是成功结束，返回 `{"items": 已取得的所有记录, "complete": True, "error": None}`。
- 中途失败必须保留已取得的记录，`complete=False`；错误为 `"http:<状态码>"`、`"timeout"`、`"budget"` 或 `"cursor"`。重复游标时保留已成功取得的页，停止循环并返回 `"cursor"`。
- 当页失败后，达到尝试上限或内层已负责重试时保留最后失败原因；尚有尝试机会但计划等待无法安排、或下一页开始前预算耗尽时返回 `"budget"`。不要把部分结果报告为完整列表。

## 任务二：创建订单

- `POST /orders`，body 为原 payload。接口约定 2xx body 中的 `id` 是已确认订单号，返回 `{"outcome": "success", "order_id": id}`。
- 只有调用方提供非空 `operation_key` 且 `now() < key_valid_until_ms` 时，服务端才保证同一键与同一正文重放不会重复创建。必须在每次额外尝试前重新检查有效期，包括等待之后；过期键不保障重放。
- 预算充足时先尝试一次；键无效只禁止额外尝试，不禁止首次请求。请求头中的幂等键只能来自本次 `operation_key`：忽略并移除请求副本里的其他旧 `Idempotency-Key`；不修改调用者头，不生成替代键。
- 无可用键、键过期或内层已重试时，不额外调用创建接口。发生过超时且最终没得到 2xx，返回 `{"outcome": "unknown", "order_id": None}`；后来的 HTTP 错误不能抹去之前可能已经创建成功的事实。其他未成功结果为 `"failed"`，无调用预算也为 failed。

评测仍用确定性故障传输器检查这些接口约定，不连接真实订单服务。不要声称没有执行过的验证已通过。


## 现有完整模块

```python
"""Existing order client to repair. Public signatures and result shapes are stable."""


def _request(send, wait, now, method, path, headers, body, budget_ms,
             attempt_timeout_ms, max_attempts, delay_ms):
    for attempt in range(max_attempts):
        headers["X-Attempt"] = str(attempt)
        try:
            response = send(method, path, headers, body, attempt_timeout_ms)
        except TimeoutError:
            continue
        if 200 <= response["status"] < 300:
            return response
        wait(delay_ms)
    return None


def list_orders(send, wait, now, headers, *, budget_ms=200,
                attempt_timeout_ms=80, max_attempts=3, delay_ms=10,
                transport_retries=False):
    items, path = [], "/orders"
    while True:
        response = _request(send, wait, now, "GET", path, headers, None,
                            budget_ms, attempt_timeout_ms, max_attempts, delay_ms)
        if response is None:
            return {"items": [], "complete": True, "error": None}
        page = response["body"]
        items.extend(page["items"])
        if not page["items"] or page["next_cursor"] is None:
            return {"items": items, "complete": True, "error": None}
        path = "/orders?cursor=" + page["next_cursor"]


def create_order(send, wait, now, headers, payload, *, operation_key=None,
                 key_valid_until_ms=None, budget_ms=200,
                 attempt_timeout_ms=80, max_attempts=3, delay_ms=10,
                 transport_retries=False):
    headers["Idempotency-Key"] = operation_key or "generated-" + str(now())
    response = _request(send, wait, now, "POST", "/orders", headers, payload,
                        budget_ms, attempt_timeout_ms, max_attempts, delay_ms)
    if response is None:
        return {"outcome": "failed", "order_id": None}
    return {"outcome": "success", "order_id": response["body"]["id"]}

```


# 本次提供的六节点技能

---
name: clarify-task
description: 把一句话或不完整的开发需求整理成可实现、可验收的任务。用于开发前澄清目标、范围和关键业务条件；已有明确需求时直接复用。
---

先查清现状，再补齐真正影响实现的条件，让开发可以开始。

- 从用户请求和目标仓库出发，读取相关说明、现有实现及项目约定；能从代码或工具确认的事实先自行查，不让用户代查。
- 说明谁遇到了什么问题、已有能力、本次要改变什么，以及明确不做什么；区分仅前端、仅后端或前后端协作。
- 把目标变成可观察的验收条件：什么输入或操作应得到什么结果，必要时包含正常、失败、权限和边界情况。不虚构业务默认值。
- 只问会改变业务含义、对外行为或实施范围的未知，并说明答案影响什么。复用已有回答；条件已清楚就结束澄清，不凑问题或反复确认。
- 输出简短任务说明：目标与范围、验收条件、已确认约束、关键未决事项。缺少关键答案时标明阻塞点，继续可独立完成的查证；不擅自选择后开始实现。
- 独立使用时交付任务说明即可；已获授权的开发流程中，把说明交给方案步骤，无需重复请求开始下一步的许可。


---
name: plain-plan
description: 生成或改写简单易懂的技术方案。用于方案设计、改造说明，或用户觉得方案太复杂、术语太多、看不懂时。
---

让不熟悉项目的人也能复述：谁遇到什么问题、原来怎么做、本次只改什么，以及怎样验证。

- 先用几句话说清问题、已有能力和推荐改动，再按需要展开；不套固定章节。
- 尊重已确定的需求和技术选择，优先复用现有能力；只添加当前需求所需的改动，保留权限、失败处理、并发和数据安全等必要约束。
- 用真实角色和具体动作讲流程：谁调用谁、处理什么、返回什么。先讲场景，再给类名、接口和参数。
- 把“治理、承载、闭环”等抽象词换成实际动作；必要术语第一次出现时，用一句话解释它在这里的意思。
- 区分已确认、推断和待确认。能自行查明的事实先查，只问会改变方案的关键问题，不虚构已有能力或调用链。
- 有多个可行方案时，只比较影响选择的区别，说明推荐哪个及原因；图表只在能帮助理解时使用。
- 交付前检查：读者能看出本次改动、关键限制和验证办法吗？仍看不懂时，换一个完整场景重讲。


---
name: implement-slice
description: 按明确需求或方案完成一个可独立验收的最小代码切片。用于前端、后端或全栈实现，保留已有改动并沿用项目约定。
---

把一个明确的行为做完整，改动范围由验收条件决定。

- 读取任务、相关代码、项目约定和当前 Git 状态，确认技术版本、已有能力与用户改动；没有单独方案文件也可从当前请求取得这些信息。
- 选一个可独立验收的切片，先复用现有实现，说明本次只改哪些位置。需求或接口存在关键歧义时先查证，必要时询问，不猜着扩展范围。
- 仅前端时依据已有接口或明确的 mock 实现，并区分未验证的集成行为；仅后端时不额外建设页面；全栈先对齐字段、错误和权限，再分别实现。只有依赖明确、写入路径不冲突时才并行。
- 沿用版本、命名、错误处理和工程设施，检查共享逻辑的受影响调用方；保留无关改动，不加入当前需求用不到的抽象、依赖或重构。
- 按改动需要维护已有测试和文档，遵守项目关于新增测试、编译及执行命令的约定和用户授权。复用已有检查；检查失败先定位原因，不删断言或放宽要求来换取通过。
- 交付改了什么、对应哪些验收条件、实际验证结果和剩余事项。实现完成不等于验证完成；在开发流程中交给验证步骤，修复后重新核对受影响结果，不自行提交、发布或扩大任务。


---
name: verify-change
description: 根据需求检查代码改动是否有效，执行适用且已获授权的工程检查并整理证据。用于实现后的验收、修复后的复验或交付前验证。
---

用实际检查说明改动是否满足需求，不把推测写成通过。

- 读取需求、差异和项目已有检查入口，确认待验证的代码版本及未提交改动。没有前序产物时从当前请求和代码补齐，关键预期不明先查证。
- 让验收条件对应适用的检查，优先复用项目的测试、构建、静态检查或已有验收脚本；验证深度随影响范围决定，不为小改动强制新增整套测试。
- 在用户授权和项目约定内执行；缺少依赖、权限或运行条件时说明具体缺口，不绕过限制，也不将未运行、跳过、超时或空结果当成成功。
- 验证正常主路径及本次相关的失败、权限和边界行为。前端操作要核对可见结果；后端检查要覆盖相关接口或数据行为；全栈区分 mock、隔离测试与真实联调证据。
- 记录关键命令、环境、退出码和报告位置，确认实际执行了目标检查；退出码为零不代表未执行的用例通过，静态检查也不等于运行成功。
- 输出已通过、失败、未验证的条件及下一步。默认不改业务代码；失败交回实现步骤，代码变化后重验受影响部分，已有且仍适用的结果可复用。


---
name: review-change
description: 结合需求和验证证据审查指定代码差异，检查改动必要性、正确性及范围内漏改。用于本地改动或指定提交、PR 的只读审查。
---

找出有证据、值得修复的问题，并说明它会怎样影响实际使用。

- 确认审查目标、比较基线、当前代码及用户要求；读取相关实现和直接调用方，不自动扩展为全仓审计。没有需求或验证资料时主动查找，仍缺失则限定结论。
- 先核改动是否必要、是否复用已有能力，再核正常路径、异常处理、权限、数据变化和兼容性；共享逻辑要看受影响调用方，范围内的遗漏也要检查。
- 核对验收条件与验证证据是否对应这版代码；测试通过不能代替代码判断，缺少测试也不自动证明存在缺陷。
- 对确认问题给出位置、触发条件、影响和最小修复方向，按影响排序。证据不足的疑点单独标明待核实，不把个人风格偏好当作阻断问题。
- 没有确认问题时直接说明，并列出影响结论的验证缺口；不把“未发现问题”写成“已通过全部验收”。
- 默认只读，不自动修复或对外发表评论。在已授权开发流程中把问题交回实现步骤；修复后检查相关差异和验证结果，满足本次要求再进入交付。


---
name: deliver-change
description: 汇总最终代码与验证结果，在已有授权内提交、推送或创建 PR，并核对对应版本的 CI。用于开发收尾或交付状态确认，不自动合并或部署。
---

交付可定位的代码和真实状态，明确区分代码已提交与 CI 已通过。

- 读取任务范围、最终差异、审查与验证结果，确认仓库、分支、远端及未提交改动；资料缺失先查，无法核实的验收项保留为未完成。
- 按用户已有授权完成本地交付、提交、推送或 PR；授权不明只确认缺少的外部动作，不重复询问已经批准的步骤。不夹带无关文件，不绕过检查，不擅自强推、合并或部署。
- 从项目工作流和分支规则确认本次必需的 CI 检查，读取对应提交或 PR 测试合并版本的状态，并核对它关联最终代码；修复后的新提交不能沿用旧提交的成功结果。
- 必需检查失败、取消、跳过、未触发或仍在运行时，说明具体任务与链接，不报 CI 完成；项目明确不适用的检查说明原因。未配置 CI 或无权读取时，也明确标为未验证。
- 等待 CI 要有界；暂时取不到结论时返回当前状态和继续检查的位置，不自动创建定时任务。失败交回相应实现或验证步骤，不降低验收条件来完成交付。
- 最后交付改动摘要、提交或 PR 链接（本地交付则给文件）、检查结果及剩余限制。只有本次要求的验收与必需 CI 都有对应证据，才声明全流程完成。
